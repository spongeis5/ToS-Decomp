# VMX128 on Xenon — a verified reference

Written 2026-08-28 for the Truth or Square decompilation, because both existing
references turned out to contain errors and neither could be trusted alone.

Everything here was checked against **three independent sources**, and where
they disagreed the disagreement was resolved rather than averaged:

| source | what it is | independent of |
|---|---|---|
| **MSVC** | `cl.exe` 15.00.8153 from XDK 8276 — the compiler that built this game, driven with `/FAsc` so it prints both the encoded word and the register names it chose | everything |
| **binutils** | the PowerPC opcode table in `ppc-dis.c`, VMX128 gated behind `PPC_OPCODE_VMX_128` | Biallas |
| **`vmx128.txt`** | Biallas, 2006, hand-documented from dumpbin output | binutils |

MSVC is the only one that is not a reconstruction. Its author's own preamble
on `vmx128.txt` reads *"I figured this out by looking at various
disassemblies, so there might be some errors"* — and there are.

---

## 1. Errata in the existing references

### 1.1 `vmx128.txt`: `vandc128` has the wrong encoding

The document gives `vandc128` and `vnor128` the **same** bit pattern:

```
line 171   vandc128  |000101| VD128 | VA128 | VB128 |A|1 0 1 0|a|1|VDh|VBh|
line 349   vnor128   |000101| VD128 | VA128 | VB128 |A|1 0 1 0|a|1|VDh|VBh|
```

They cannot both be right. MSVC settles it:

```
__vandc -> vandc128  143FF271   bits 22..25 = 1001
__vnor  -> vnor128   143FF2B1   bits 22..25 = 1010
__vand  -> vand128   143FF231   bits 22..25 = 1000
__vor   -> vor128    143FF2F1   bits 22..25 = 1011
```

**`vandc128` is `1001`.** The document's `1010` is `vnor128`'s value. binutils
already has it right. Across 32 forms compared, this is the *only* disagreement
between binutils and the document.

### 1.2 binutils: `vupkhsb128` / `vupklsb128` print a phantom operand

```
{ "vupkhsb128", VX128(6, 896), VX128_MASK, PPCVEC128, { VD128, VB128, VA128 }, ... }
                                                                     ^^^^^^
```

The instruction takes two operands. binutils declares three, so it prints the
reserved zero field at bits 11..15 as a register:

```
1A607B85   MSVC:     vupkhsb128 vr51,vr47
           binutils: vupkhsb128 v51,v47,v0
```

The **encoding is read identically** — `VD128=19, VDh=1 -> vr51`;
`VB128=15, VBh=1 -> vr47` — so this is a disassembly-text defect, not a decode
error. It affects `vupkhsb128` and `vupklsb128`.

### 1.3 Minor: the document's `vupklsb128` example line reads `vupkhsb128`

`vmx128.txt` line 603 gives the mnemonic in `vupklsb128`'s usage example as
`vupkhsb128`. A copy-paste slip; the bit pattern above it is correct.

## 2. How the encoding works

Bit numbering is IBM style throughout: **bit 0 is the most significant bit** of
the 32-bit word, exactly as `vmx128.txt` draws it.

### 2.1 Registers are split across the word

This is the part that matters and the part a careless transcription gets wrong.
A VMX128 register number is 7 bits (0..127) assembled from separate fields:

```
VD  =  (VDh << 5) | VD128          VDh at bits 28..29,  VD128 at bits 6..10
VB  =  (VBh << 5) | VB128          VBh at bits 30..31,  VB128 at bits 16..20
VA  =  (A << 6) | (a << 5) | VA128    A at bit 21, a at bit 26, VA128 at 11..15
VC  =  3 bits only (vr0..vr7)      at bits 22..24
```

Worked example, from MSVC's own listing:

```
17bef8b5   vmulfp128  vr61,vr62,vr63

  bits  0..5   000101   primary opcode 5
  bits  6..10  11101    VD128 = 29
  bits 11..15  11110    VA128 = 30
  bits 16..20  11111    VB128 = 31
  bit  21      0        A
  bits 22..25  0010     extended opcode = vmulfp128
  bit  26      1        a
  bit  27      1        form selector
  bits 28..29  01       VDh = 1   ->  VD = (1<<5)|29 = 61   vr61
  bits 30..31  01       VBh = 1   ->  VB = (1<<5)|31 = 63   vr63
                                       VA = (0<<6)|(1<<5)|30 = 62   vr62
```

### 2.2 The `128` suffix is a register-allocation outcome

**There is no separate "VMX128 intrinsic".** The same intrinsic emits the plain
VMX encoding when its operands land in `vr0..vr31` and the 128 encoding when
they do not:

```
__vmaddfp(a,b,c)  ->  vmaddfp    vr1,vr0,vr13,vr12     (low registers)
__vmaddfp(a,b,c)  ->  vmaddfp128 vr61,vr62,vr63,...    (under pressure)
```

The retail image contains both forms of the same operations — `vmaddfp` 3,971
sites beside `vmaddfp128` 152, `vspltisw` 254 beside `vspltisw128` 244.

For decompilation this is the useful fact: **write the intrinsic and reproduce
the function's register pressure**, and the allocator produces the encoding the
original had. You do not choose the encoding directly.

### 2.3 The seven instruction forms

binutils encodes each form as `opcode = (op << 26) | (xop & C)` with
`mask = (0x3F << 26) | C`:

| macro | C | fields it fixes |
|---|---|---|
| `VX128` | `0x3D0` | bits 22..25 (4-bit xo), bit 27 |
| `VX128_1` | `0x7F3` | bits 21..27 (7-bit xo), bits 30..31 — loads/stores |
| `VX128_2` | `0x210` | bits 22, 27 — `vperm128`, which needs VC |
| `VX128_3` | `0x7F0` | bits 21..27 — one source operand + immediate |
| `VX128_4` | `0x730` | `vrlimi128` |
| `VX128_5` | `0x010` | `vsldoi128`, which needs SHB |
| `VX128_P` | `0x630` | `vpermwi128`, split immediate |

## 3. Verification performed

Every claim above is backed by a check over the whole retail image, not a
sample. Tools are in `tools/`; each is re-runnable.

**Decode completeness** — `tools/ppcdis.py`

```
opcode-4/5/6 instruction words in .text   58,976
  a VMX128 form                           44,956  (76.2%)
  plain VMX/Altivec                        14,020  (23.8%)
  UNDECODED                                     0  (0.00%)
```

**Table unambiguity** — `tools/vmx128_table.py`

```
distinct opcode-4/5/6 words   24,363
  matching exactly one entry  18,983
  matching none (plain VMX)    5,380
  matching MORE THAN ONE            0
```

**Information preservation** — the strongest check, and it needs no reference
material at all. If any operand field were being ignored, two words differing
only in that field would print identically:

```
distinct words           24,363
distinct decode strings  24,363
colliding decodes             0
```

**No impossible instructions.** IBM removed 22 VMX instructions in VMX128
(`vmuloub`, `vsum4ubs`, `vmhaddshs`, `vmsumshs`, …). A decode naming one of
them would be wrong:

```
words decoding to a removed instruction: 0
```

**Record forms are handled.** `vcmpequw.`, `vcmpequw128.`, `vcmpgtfp128.` all
decode, so the R bit is read.

**Against Biallas** — `tools/vmx128_check.py`: 16 forms transcribed from the
document, 14,617 words checked, agreement on mnemonic **and** reassembled
register numbers, 0 disagreements.

**Against MSVC** — `tools/vmx128_oracle.py`: 138 instructions, 33 forms, 64
distinct registers of which **32 above `vr31`** (without high registers the
split fields are all zero and the check passes vacuously). 136 agree; the 2
that do not are §1.2.

## 4b. Oracle coverage, form by form

Asked three times whether this was finished, and the third pass found two real
gaps. Both are now closed:

**Plain VMX/Altivec was never operand-checked.** The MSVC oracle filtered on
mnemonics ending in `128`, leaving the 14,020 plain instructions (23.8% of the
vector code) validated by nothing. Re-run over every intrinsic at low register
pressure: **125 forms, 125 agree, 0 mismatches.**

A first attempt reported 11 mismatches. All eleven were a defect in the
comparison, not the decoder: normalising `vr1` to `v1` with a blanket
`replace("vr","v")` also corrupts any mnemonic *containing* "vr" —
`vrefp`→`vefp`, `vrfim`→`vfim`, `vrlw`→`vlw`, `vrsqrtefp`→`vsqrtefp`. The
twelfth apparent mismatch, `lvlx v1,r0,r3` against `v1,0,r3`, is the RA==0
convention, where binutils prints a bare `0`.

**Immediates were validated at one value each.** `vpermwi128` carries a SPLIT
immediate (`PERMh<<5 | PERMl`) across 1,578 sites; swapped halves would survive
every other test here, including the collision test, because the swap is
bijective. Swept across the range — `vpermwi128` at 0, 1, 2, 3, 7, 27, 31, 63,
99, 127, 200, 255, plus `vsldoi128`, `vspltw128`, `vcsxwfp128`:
**30 cases, 30 agree, 0 mismatches.**

### Where each form's confidence comes from

```
forms present in the image                   56
  confirmed by MSVC's own encoder            45
  of the rest, confirmed by the doc           2   (lvlx128, stvlx128)
  binutils + structural tests only            9   (1,334 sites, 3.0%)
```

The 9 are `stvewx128`, `vspltisw128`, `vmaddcfp128`, `vmaddfp128`, `lvrx128`,
`vpkd3d128`, `stvrx128`, `vnmsubfp128`, `lvewx128`. The compiler declines to
emit the 128 encoding for them even under heavy register pressure — it uses the
plain form — so MSVC cannot be made to confirm them without hand-written
assembly, and `ml.exe` predates the extension.

They are not unverified. Every one participates in: 0 undecoded across 58,976
words, 0 ambiguous across 24,363, 0 decode-string collisions, and 0 decodes
naming an instruction Xenon does not implement. What they lack is a second
*encoder* saying the same thing.

## 5. What is NOT established

- **`vmaddcfp128` (175 sites) and `vpkd3d128` (94)** have no declared intrinsic
  in `ppcintrinsics.h` or `vectorintrinsics.h`. Whether ordinary vector
  expressions reach them is untested. Decoding them is fine; *writing* them may
  not be, and that only matters when matching a function that contains one.
- **Semantics.** This document covers encoding, not behaviour. `vmx128.txt`
  marks `vpkd3d128`'s `x, y, z` fields as unknown immediates and this work did
  not change that.
- **Ghidra cannot decode VMX128.** Issue #2094, open since 2020, no mainline
  support. Forks exist (pjsoberoi; 0dinD's rebase onto Ghidra 12.0, which also
  corrects errors in both the SLEIGH and the documentation) and are untried
  here. This project's own tools decode it; inside Ghidra the words remain
  undefined, and `ghidra_scripts/ApplyKnowledge.java` only resumes disassembly
  *after* each one rather than decoding it.
